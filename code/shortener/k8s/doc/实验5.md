# 实验五：资源限制观测——OOMKilled 与 CPU 节流

## 实验目标

在 Kubernetes 中实际触发并确认容器 OOM，同时采集 CPU 限额下的实际用量与节流计数。实验使用独立、临时的测试 Pod；不向正在提供服务的 API 副本施加内存压力，也不修改 API Deployment 的资源配置。

## 实验环境与安全边界

| 项目 | 实测值 |
|---|---|
| Kubernetes context | `kind-shortener` |
| 集群节点 | `shortener-control-plane` |
| Namespace | `shortener` |
| 测试镜像 | `busybox:1.36`，`imagePullPolicy: Never` |
| 测试 Pod | `experiment5-oom-20261010` |
| 重启策略 | `Never`，保留容器终止状态，不自动重启 |
| 内存 request / limit | `8Mi` / `16Mi` |
| 内存压力方式 | 将 64 MiB 零数据写入 memory-backed `emptyDir` |
| CPU 测试 Pod | `experiment5-cpu-20261010`，`busybox:1.36` |
| CPU request / limit | `50m` / `100m` |
| CPU 压力方式 | BusyBox shell 忙循环，受容器 CPU quota 限制 |
| CPU 采集方式 | Metrics Server (`kubectl top`) 与 cgroup v2 `/sys/fs/cgroup/cpu.stat` |
| 安全隔离 | 测试独立 Pod，不属于 API Deployment，也不匹配 API Service selector |

实验开始前，API Deployment 为 `2/2` Ready，API Service EndpointSlice 有两个后端地址。Metrics Server 已就绪；两种压力测试都使用独立 Pod，不改变 API 的资源声明。

## 操作步骤

### 1. 确认 context 和 API 基线

```bash
kubectl config current-context
kubectl get deployment api -n shortener
kubectl get pods -n shortener -l app=api -o wide
kubectl get endpointslices -n shortener \
  -l kubernetes.io/service-name=api -o wide
curl -i --max-time 5 http://localhost:8080/api/healthz
```

本次基线：API Deployment 为 `2/2`；两个 API Pod 为 `1/1 Running`，重启次数均为 `0`；EndpointSlice 包含 `10.244.0.20` 和 `10.244.0.21`；健康检查返回 HTTP 200。

### 2. 准备测试镜像

kind 节点使用独立的 containerd 镜像存储。测试镜像从本机 Docker 镜像存储导出并导入 kind 节点，然后在 Pod 中使用 `imagePullPolicy: Never`，不依赖节点访问镜像仓库。

```bash
docker image save --platform linux/amd64 \
  -o /tmp/busybox-1.36-amd64.tar busybox:1.36
kind load image-archive /tmp/busybox-1.36-amd64.tar --name shortener
rm /tmp/busybox-1.36-amd64.tar
docker exec shortener-control-plane crictl images | grep 'busybox.*1.36'
```

实验时，节点已有 `busybox:1.36` 镜像；Pod Events 也确认镜像已存在并成功启动。

### 3. 创建隔离的内存压力 Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: experiment5-oom-20261010
  namespace: shortener
  labels:
    app.kubernetes.io/name: experiment5-oom
    app.kubernetes.io/part-of: shortener
spec:
  restartPolicy: Never
  activeDeadlineSeconds: 60
  containers:
    - name: allocator
      image: busybox:1.36
      imagePullPolicy: Never
      command: ["dd", "if=/dev/zero", "of=/memory/payload", "bs=1M", "count=64"]
      resources:
        requests:
          memory: 8Mi
        limits:
          memory: 16Mi
      volumeMounts:
        - name: memory
          mountPath: /memory
  volumes:
    - name: memory
      emptyDir:
        medium: Memory
        sizeLimit: 64Mi
```

执行创建并观察：

```bash
kubectl apply -f oom-pod.yaml
kubectl get pod experiment5-oom-20261010 -n shortener -w
```

Pod 很快经历 `ContainerCreating`、`Running`，随后状态变为 `OOMKilled`。这里的 `OOMKilled` 是 kubectl 对终止容器的展示；Pod 终态为 `Failed`，容器退出原因及退出码见下方取证结果。

## 对业务服务的影响与恢复验收

测试 Pod 运行期间检查 API：

```text
deployment/api:  2/2 READY
API Pod:         2 个，均为 1/1 Running，RESTARTS 0
API endpoints:  10.244.0.20, 10.244.0.21
GET /api/healthz: HTTP/1.1 200 OK
Body:            {"status":"ok"}
```

采集完终止状态与 Events 后清理临时 Pod：

```bash
kubectl delete pod experiment5-oom-20261010 -n shortener --wait=true
kubectl get pod experiment5-oom-20261010 -n shortener --ignore-not-found
kubectl get deployment api -n shortener
kubectl get endpointslices -n shortener \
  -l kubernetes.io/service-name=api -o wide
curl -i --max-time 5 http://localhost:8080/api/healthz
```

实际恢复验收结果：Pod 删除命令确认删除成功；随后查询没有返回该测试 Pod；API Deployment 仍为 `2/2`，EndpointSlice 仍有两个 API 地址，健康检查再次返回 HTTP 200。

## CPU 用量与节流采集

### 测试配置

使用独立 CPU 测试 Pod，以 request `50m`、limit `100m` 运行持续忙循环。`activeDeadlineSeconds` 设为 180 秒作为兜底时限；采集完成后主动删除 Pod。测试 Pod 不接收 API Service 流量。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: experiment5-cpu-20261010
  namespace: shortener
  labels:
    app.kubernetes.io/name: experiment5-cpu
    app.kubernetes.io/part-of: shortener
spec:
  restartPolicy: Never
  activeDeadlineSeconds: 180
  containers:
    - name: burner
      image: busybox:1.36
      imagePullPolicy: Never
      command: ["sh", "-c", "while :; do :; done"]
      resources:
        requests:
          cpu: 50m
          memory: 8Mi
        limits:
          cpu: 100m
          memory: 16Mi
```

等待 Pod Ready 后持续采样，`kubectl top` 第一次出现 `NotFound` 是因为 Metrics Server 尚未完成新 Pod 的首次采集。首轮之后继续读取，而不是将指标缺失当成 0：

```bash
kubectl wait --for=condition=Ready pod/experiment5-cpu-20261010 \
  -n shortener --timeout=30s
kubectl top pod experiment5-cpu-20261010 -n shortener --containers
kubectl exec experiment5-cpu-20261010 -n shortener -- \
  cat /sys/fs/cgroup/cpu.stat
```

### 实际采集结果

Pod 在 `2026-10-10 15:19` 左右启动。初始两次 `kubectl top` 因 Metrics Server 尚无该 Pod 的指标返回 `NotFound`，同一时段的 cgroup 计数器已显示负载及节流在增长。后续采样结果如下：

| 采样时间（+08:00） | `kubectl top` CPU | 内存 |
|---|---:|---:|
| 15:20:07 | `98m` | `0Mi` |
| 15:20:23 | `100m` | `0Mi` |
| 后续采样 | `101m` | `0Mi` |

最终读取的 cgroup v2 计数器：

```text
usage_usec      7634926
user_usec       7595722
system_usec       39203
nr_periods          763
nr_throttled        746
throttled_usec  11689426
nr_bursts             0
burst_usec            0
```

`nr_throttled / nr_periods = 746 / 763 ≈ 97.8%`。CPU 用量采样接近 `100m` limit，且 cgroup 明确记录了大量被节流周期，证明这个受限 CPU 忙循环确实受到 quota 节流。`kubectl top` 是采样窗口上的近似值，显示 `101m` 不表示容器持续超过 limit；它与 cgroup 累积计数的观测口径不同。

Pod 状态为 `Running`、重启次数为 `0`，符合 CPU quota 通常限制执行时间而不会直接杀死进程的行为。这里测量的是专门的 CPU burner，而不是 API 请求吞吐或 API Pod 自身的节流率；因此不能将这些数值解释为 API 性能基准。

### CPU 测试恢复

采集完 CPU 指标与 cgroup 计数器后，停止负载并删除临时 Pod：

```bash
kubectl delete pod experiment5-cpu-20261010 -n shortener --wait=true
kubectl get pod experiment5-cpu-20261010 -n shortener --ignore-not-found
```

删除命令确认 Pod 已删除，随后查询没有返回该 Pod。CPU burner 退出后，API Deployment 仍为 `2/2`，API Service EndpointSlice 仍有两个后端，`/api/healthz` 再次返回 HTTP 200。

## 结论

本次在隔离测试容器中**实际触发并确认了 OOMKilled**：容器内存 limit 为 `16Mi`，写入内存型临时卷的分配操作导致容器以 `OOMKilled`、退出码 `137` 终止。Pod 使用 `restartPolicy: Never`，因此终止后重启次数为 `0`，并保留了可检查的失败状态。

CPU 测试中，独立 burner Pod 的 CPU 用量达到约 `98–101m`，对应 `100m` limit；cgroup 统计 763 个周期中有 746 个发生节流。该结果确认临时 CPU 负载受到 quota 节流，但不是 API 吞吐性能对比。

两项实验都只作用于临时测试 Pod，不是 API 容器 OOM，也没有改变 API 的 CPU 配置。采集后测试 Pod 均已删除；API 始终保持两个 Ready 副本、两个 Service 后端，健康检查返回 HTTP 200，实验环境恢复完成。

## 诊断要点

- `OOMKilled` 是容器终止原因；退出码 `137` 与收到 `SIGKILL` 相符。结合容器状态中的 `Reason: OOMKilled`，可确认本次容器因 OOM 被终止。
- `restartCount: 0` 不表示没有发生 OOM：本 Pod 的 `restartPolicy: Never`，所以容器终止后不会在 Pod 内重启。
- Deployment 更新时旧 Pod 被新 ReplicaSet 替换，不等同于同一容器被 OOM 杀死；应检查容器 `Last State`、终止原因、退出码和 Pod Events。
- `kubectl logs --previous` 查询的是同一 Pod 上一次已终止容器的日志，不用于查询已删除的另一个 Pod。本次测试容器被快速杀死，没有可用进程日志，状态字段保留了关键证据。
- 将 memory limit 调低本身不会触发 OOM；必须有进程实际使用超过容器限额。本实验通过写入 memory-backed `emptyDir` 产生了可控内存压力。
- `kubectl top` 提供近期 CPU 采样，首次查询可能因 Metrics Server 尚未采到新 Pod 而无数据；应稍后重试，不能把 `NotFound` 当成 0 CPU。
- cgroup v2 的 `cpu.stat` 中，`nr_periods` 是调度周期数，`nr_throttled` 是发生节流的周期数，`throttled_usec` 是累计节流时间。与 `kubectl top` 结合，可分别观察近实时用量和 quota 节流计数。
