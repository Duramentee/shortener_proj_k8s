# 实验二：Readiness Probe 配置错误与发布阻塞

## 面试复盘卡

### 一句话结论

将 API 的 Readiness Probe 路径配置为不存在的 `/api/not-exist` 后，新 Pod 仍能运行，但探针收到 HTTP 404，因此 Pod 未 Ready，Deployment rollout 无法完成。故障源于健康检查配置，不是应用进程崩溃。

### 场景与故障注入

- **故障对象：** `api` Deployment 的 Pod 模板中的 `readinessProbe.httpGet.path`。
- **注入方式：** 使用 JSON Patch 将探测路径改为 `/api/not-exist`。
- **预期影响：** 应用进程仍可启动，但 Kubernetes 的 HTTP Readiness Probe 持续失败；新 Pod 不会被认为已就绪，滚动更新可能停滞或超时。
- **实际记录：** rollout 等待 `1 out of 2 new replicas` 后超时；两个旧副本为 `1/1 Running`，新 Pod 为 `0/1 Running`，重启次数为 `0`。Events 明确记录探针返回 HTTP 404。

### 诊断链路

1. **从发布状态识别异常：** `kubectl rollout status` 超时只表示 Deployment 未达到期望状态，不直接说明故障根因。
2. **区分进程状态与就绪状态：** 新 Pod 的 `STATUS` 为 `Running`，但 `READY` 为 `0/1`，且 `RESTARTS` 为 `0`。容器在运行，不代表 Pod 已具备接收 Service 流量的条件。
3. **检查探针配置和 Events：** `kubectl describe pod` 显示探针路径为 `/api/not-exist`；Events 中的 `Readiness probe failed ... statuscode: 404` 将症状定位到 HTTP 路由/探针配置。
4. **评估发布及业务影响：** 旧副本仍 Ready，新副本未 Ready。现有日志并未记录完整的 EndpointSlice readiness condition，因此如需精确说明新 Pod 是否处于 Service 可用端点集合，应补查 EndpointSlice 的 `conditions.ready`。

### 根因与 Kubernetes 机制

Readiness Probe 用于判断容器是否适合接收流量。HTTP 探针通常将成功状态码范围内的响应判定为成功；404 表示服务端可响应请求，但请求路径不存在，不满足就绪条件。Readiness 失败会使 Pod 保持未就绪，控制器据此不会将其计入可用副本，也可能阻止滚动更新继续推进。

Readiness Probe 与 Liveness Probe 的作用不同：Readiness 失败不会直接重启容器；Liveness 连续失败达到阈值后，kubelet 才会重启容器。因此单独看到 `Running`、`0` 次重启并不能说明服务就绪，必须同时检查 `READY`、探针事件及控制器状态。

### 恢复与验证

执行 `kubectl rollout undo deploy/api -n shortener` 后，rollout status 确认回滚成功；API Deployment 恢复到 `shortener-api:dev`，两个副本均为 Ready。随后发现 `localhost:8080` 无法连接，是因为本机端口转发未运行；重新启动 `kubectl port-forward -n shortener svc/web 8080:80` 后，`/api/readyz` 返回 HTTP 200，依赖检查 PostgreSQL、Redis 均为 `ok`。

### 面试表达示例

> 我通过修改 Deployment 的 Readiness Probe 路径注入故障。新 Pod 显示 `Running` 但 `0/1 Ready`，重启次数为 0，rollout 卡在新副本不可用；Pod Events 进一步显示探针请求返回 404。由此我定位到探针路径配置错误，而不是应用进程崩溃。Readiness 失败影响 Pod 是否接收流量和 Deployment 的发布进度，但不会像 Liveness 失败那样直接触发重启。我用 rollout undo 恢复配置，确认两个副本 Ready，再恢复本机端口转发并验证依赖检查通过。

### 常见追问

- **Readiness 失败会重启容器吗？** 不会。它影响 Pod 的就绪状态与流量接收；重启行为通常由 Liveness Probe 失败触发。
- **`Running` 和 `Ready` 为什么必须分开判断？** `Running` 表示容器处于运行状态；`Ready` 表示 Pod 满足就绪条件，适合接收流量。依赖不可用、探针失败等情况都可能造成 Running 但 NotReady。
- **rollout status 超时意味着什么？** 表示在设定时间内 Deployment 未满足滚动更新条件；应进一步检查 Pod 状态、探针、Events、ReplicaSet 和副本数，而不是把超时本身当作根因。
- **如何证明端点已被摘除？** 检查 API Service 对应 EndpointSlice 中每个端点的 `conditions.ready`，并结合流量验证；只看地址列表不足以判断 Ready 条件。

## 实验结论

- 实验已完成。将 API 的 `readinessProbe` 路径改为不存在的 `/api/not-exist` 后，新 Pod 持续处于 `Running` 但未就绪（`0/1`），容器重启次数为 `0`；Events 中的 HTTP 404 表明探针配置错误导致 Pod 未通过就绪检查，并非应用进程崩溃。
- 执行 `kubectl rollout undo deploy/api -n shortener` 后，Deployment 成功回滚至 `shortener-api:dev`，两个副本均为 Ready。回滚命令中的注解警告不代表回滚失败。
- 回滚后访问 `localhost:8080` 曾因端口转发未运行而连接失败；重新启动 `kubectl port-forward -n shortener svc/web 8080:80` 后，`/api/readyz` 返回 HTTP 200，PostgreSQL 和 Redis 检查均为 `ok`。
