# 实验三：Service Selector 不匹配与无可用后端

## 面试复盘卡

### 一句话结论

API Pod 本身仍为 `Running` 且 Ready，但 API Service 的 selector 被改为与 Pod 标签不匹配的值，导致 EndpointSlice 没有后端端点；经 Web 入口访问 API 返回 HTTP 502。故障位于 Service 到 Pod 的服务发现/流量转发链路，而非 API 进程。

### 场景与故障注入

- **故障对象：** `shortener` 命名空间中的 `api` Service。
- **注入方式：** 将 Service selector 从 `app=api` 改为 `app=api-lab-mismatch`。
- **实际影响：** API Deployment 中的两个 Pod 仍为 `1/1 Running`；Service selector 找不到标签匹配的 Pod，EndpointSlice 的 `endpoints` 为空；Web 代理访问 API 时返回 502。

### 诊断链路

1. **确认用户侧症状：** `curl http://localhost:8080/api/healthz` 返回 HTTP 502，响应由 Nginx 返回。
2. **检查工作负载：** `kubectl get pods -n shortener -l app=api` 显示两个 API Pod 都 Ready，排除“所有 API 容器均未运行”这一初始假设。
3. **检查 Service 选择条件：** `kubectl get svc api -o yaml` 显示 selector 为 `app: api-lab-mismatch`；API Pod 标签为 `app=api`，二者不一致。
4. **检查控制面生成的后端：** API Service 对应 EndpointSlice 显示 `endpoints: null`。Service 没有可转发的后端，解释了代理无法连接 API 后端的 502。

### 根因与影响范围

Service 通过 selector 选择带有匹配标签的 Pod，控制器据此维护 EndpointSlice。selector 本身语法有效，因此 API 对象仍存在、ClusterIP 也仍分配，但这并不保证有可用后端。错误 selector 造成“Service 存在但无端点”的情况。

本次观测能够证明经 Web 代理的 API 请求失败以及 API Service 没有匹配端点；不能据此推断 API 进程崩溃，也没有记录页面首页或所有业务入口均不可用。应按真实受影响路径描述影响，避免把局部 API 故障扩大成整个应用完全中断。

### 恢复方法与验证

将 selector 改回与 API Pod 标签一致的 `app=api`，然后检查 EndpointSlice 是否重新生成端点，并从实际入口验证 API：

```bash
kubectl patch svc api -n shortener --type=merge \
  -p='{"spec":{"selector":{"app":"api"}}}'
kubectl get endpointslice -n shortener \
  -l kubernetes.io/service-name=api -o yaml
curl -i http://localhost:8080/api/healthz
```

**记录完整性说明：** 当前实验日志保留了故障注入、Pod、Service、EndpointSlice 和 HTTP 502 的输出，但没有保留恢复 selector 后的命令及验证输出。实验虽已完成，若用于展示故障闭环，建议补记实际恢复结果，不要将上述参考命令表述为已采集的实测输出。

### 面试表达示例

> 我把 API Service 的 selector 从 `app=api` 改成了不匹配的标签。用户侧通过 Web 访问 API 得到 Nginx 502，但两个 API Pod 仍然是 Ready。随后我对照 Service selector 和 Pod labels，发现标签不一致；EndpointSlice 中端点为空，确认故障位于 Service 后端发现链路，而不是应用进程。恢复时应将 selector 设回 `app=api`，再以 EndpointSlice 重新出现就绪端点、API 健康请求恢复 200 作为验收条件。

### 常见追问

- **为什么 Service 和 ClusterIP 仍存在却无法访问？** Service 对象和虚拟 IP 的存在不代表存在可用后端；没有匹配 selector 的 Pod 时，EndpointSlice 不包含可转发端点。
- **HTTP 502 能否直接证明 API 崩溃？** 不能。502 描述代理无法从上游获得有效响应；需继续检查 Service、EndpointSlice、Pod Ready、网络和应用日志。
- **排查 selector 时要对比什么？** 对比 Service `spec.selector` 与 Pod metadata labels 的键和值，并确认同一命名空间及 EndpointSlice 中端点状态。

## 实验结论

- 实验已完成。将 API Service 的 selector 从 `app=api` 改为 `app=api-lab-mismatch` 后，后端 Pod 仍为 `Running` 且 Ready，但 EndpointSlice 中没有端点，说明 Service selector 未匹配到 Pod。
- 访问经由 Web 的 `/api/healthz` 返回 HTTP 502，与“Service 无可用后端”的诊断相符；该故障由 Service 配置错误导致，并非 API Pod 崩溃。
