# 实验一：镜像拉取失败与 Deployment 发布阻塞

## 面试复盘卡

### 一句话结论

新 API Pod 因镜像不可用而无法启动，处于 `ImagePullBackOff`，而不是应用进程启动后崩溃。原有两个副本仍为 Ready，因此实验记录能证明新版本发布受阻和副本冗余下降，但不能据此断言服务完全中断。

### 场景与故障注入

- **故障对象：** `shortener` 命名空间中的 `api` Deployment。
- **注入方式：** 将 API 容器镜像从 `shortener-api:dev` 改为 `shortener-api:notexist`。
- **预期影响：** Deployment 创建新 ReplicaSet；新 Pod 无法取得所需镜像，无法进入 Ready，滚动发布不能完成。
- **关键参数：** 实验记录中的 Deployment 使用 `imagePullPolicy: IfNotPresent`。当节点本地没有指定镜像时，kubelet 会尝试从镜像仓库拉取。

### 观测结果与证据

| 观测项 | 实验记录 | 诊断意义 |
|---|---|---|
| 新 Pod 状态 | `ImagePullBackOff`，容器 `Waiting` | 失败发生在容器启动前的镜像准备阶段 |
| 新 Pod 重启次数 | `0` | 没有证据表明应用容器曾启动后退出 |
| 旧副本 | 两个 Pod 均为 `1/1 Running` | 旧版本仍可用；发布阻塞不等于已发生全站中断 |
| Events | 尝试拉取 `docker.io/library/shortener-api:notexist`，连接代理 `127.0.0.1:9674` 被拒绝 | 明确证明本次拉取请求未成功；代理错误本身不能证明远端标签不存在 |
| EndpointSlice | 输出包含 Pod IP，但未记录端点 `conditions.ready` | 不能只凭地址列表断言失败 Pod 是否被 Service 当作 Ready 后端 |

### 根因判断及证据边界

本次直接故障是新 Pod 无法获得其声明的容器镜像。`ImagePullBackOff` 是 kubelet 对镜像拉取失败进行退避重试时的状态，并不是应用程序返回的错误，也不等同于 `CrashLoopBackOff`。

Events 中出现了远端镜像引用及代理连接拒绝。由于请求在连接代理阶段失败，本次证据**不能区分**以下情况：镜像标签在仓库中不存在、仓库暂时不可达、代理配置或代理进程异常。实验目标标签虽为 `notexist`，但不能把预期故障注入描述成已证实的远端仓库事实。

若需区分“镜像引用错误”与“镜像没有加载到 kind 节点”，应依次核对 Deployment/Pod 的完整镜像引用、`imagePullPolicy`、Events 的具体错误，并在实际承载 Pod 的 kind 节点内检查 `crictl images`。宿主机的 `docker images` 只反映宿主机 Docker 镜像存储，不能代表节点 containerd 的镜像清单。

### 恢复与验证

实验后执行了 `kubectl rollout undo deploy/api -n shortener`。随后 `kubectl rollout status` 报告 Deployment 成功发布，API 恢复为 `shortener-api:dev` 且两个副本 Ready。undo 输出中的 `last-applied-configuration` 警告是关于声明式配置注解未同步的提示，不代表回滚失败；长期维护时应以仓库中的 YAML 为配置事实来源，并在需要时用原清单重新 `kubectl apply`。

回滚后 `curl localhost:8080` 一度连接失败，原因是本机没有运行端口转发进程，而非 API Deployment 再次故障。重新启动 `kubectl port-forward -n shortener svc/web 8080:80` 后，`/api/readyz` 返回 HTTP 200，PostgreSQL 与 Redis 检查均为 `ok`。这说明访问链路还包含本机端口转发这一独立环节。

### 面试表达示例

> 我在 kind 集群中把 API Deployment 的镜像改成了一个不可用标签，观察到新 Pod 进入 `ImagePullBackOff`，容器重启次数为 0，而旧的两个副本仍为 Ready。`describe pod` 和 Events 显示 kubelet 尝试访问 Docker Hub，但请求在连接本机代理时被拒绝。因此我判断故障发生在镜像拉取阶段，应用进程尚未启动；同时我没有把代理连接错误误判为远端标签不存在。之后通过 rollout undo 恢复到 `shortener-api:dev`，确认两个副本 Ready，并重新启动端口转发验证 `/api/readyz` 返回 200。这个实验让我区分了镜像拉取故障、进程崩溃和本地访问链路故障。

### 常见追问

- **`ImagePullBackOff` 与 `CrashLoopBackOff` 有何不同？** 前者表示 kubelet 无法取得镜像，容器通常尚未成功启动；后者表示容器启动后退出并被反复重启。应结合 `State`、`Last State`、重启次数和 Events 判断。
- **为什么 `docker images` 不能证明 kind 节点已有镜像？** kind 节点是独立容器，Kubernetes 工作负载镜像由节点内的 containerd 管理；应进入对应节点检查 `crictl images`。
- **`IfNotPresent` 是否一定本地优先？** 节点存在匹配镜像时可使用本地镜像；不存在时需要从镜像仓库获取。还应核实完整镜像名与标签是否精确匹配。
- **如何安全恢复？** 回滚 Deployment revision 后等待 rollout 完成，再核对镜像、期望/可用副本、Pod Ready 状态及业务健康接口；同时确保配置文件与集群状态一致。

## 实验结论

- 实验已完成。API 新 Pod 处于 `ImagePullBackOff`，容器重启次数为 `0`；故障发生在镜像拉取阶段，应用进程尚未启动，不属于应用崩溃。
- Deployment 使用 `imagePullPolicy: IfNotPresent`。事件记录显示节点尝试从 Docker Hub 拉取 `shortener-api:notexist`，但本机代理连接被拒绝。该证据证明拉取失败，不能单独证明远端镜像标签是否存在。
- 区分镜像引用错误与本地镜像未加载时，应核对 Deployment/Pod 的镜像引用、`imagePullPolicy`、Events 中的具体错误，并在对应 kind 节点执行 `crictl images` 检查。宿主机的 `docker images` 不能代替节点镜像清单。
