# 实验六：Redis Service 无可用端点与探针配置观察

## 面试复盘卡

### 一句话结论

将 Redis Service 的 selector 改为不匹配的标签后，EndpointSlice 中没有 Redis 后端；恢复 selector 后，端点重新出现为 `10.244.0.8:6379`。记录中的 API Pod 在 selector 不匹配时仍显示 `Running` 且 `Ready`，但没有保存故障期间的业务请求或 API 健康检查结果，因此只能确认 Redis Service 后端发现异常，不能据此断言 API 业务请求已经失败。

### 场景与故障注入

- **故障对象：** `shortener` 命名空间中的 `redis` Service。
- **注入方式：** 将 selector 从 `app=redis` 改为 `app=redis-lab-mismatch`。
- **相关探针变更：** 记录还将 API Deployment 的 Liveness Probe 路径从 `/api/healthz` 改为 `/api/readyz`，之后又恢复为 `/api/healthz`。两次 rollout 均成功；记录没有显示这项路径变更单独造成探针失败。

### 诊断链路

1. **确认 Service 后端状态：** Redis selector 被改动后，EndpointSlice 的 `PORTS`、`ENDPOINTS` 均为空，说明没有 Pod 被该 Service selector 选中。
2. **区分 API Pod 与 Redis Service 状态：** selector 不匹配期间，两个 API Pod 均显示 `1/1 Running`，`describe` 输出中也显示 Pod Ready。容器仍在运行并不等于 Redis Service 有可用后端。
3. **验证恢复：** 将 Redis selector 改回 `app=redis` 后，EndpointSlice 显示端口 `6379` 和端点 `10.244.0.8`；恢复 API Liveness Probe 路径并完成 rollout 后，`/api/readyz` 返回 HTTP 200，PostgreSQL、Redis 检查均为 `ok`。

### 根因与 Kubernetes 机制

Service 根据 `spec.selector` 选择同一命名空间内标签匹配的 Pod，并由控制器据此维护 EndpointSlice。selector 值与 Redis Pod 标签不匹配时，Service 对象仍然存在，但没有可转发的后端端点。

这份实验记录证明了 selector 不匹配与 EndpointSlice 无端点之间的对应关系。由于没有保存 selector 错误期间的 Redis Pod 标签/状态、API 健康请求或业务请求结果，不应补写“API 已不可用”或“Redis Pod 已故障”等未被记录证明的结论。

**探针设计提示：** Liveness Probe 用于判断进程是否需要重启，Readiness Probe 用于判断 Pod 是否适合接收流量。若 `/api/readyz` 会因 Redis 等依赖短暂不可用而失败，将它用作 Liveness 路径可能导致不必要的容器重启；通常应让 Liveness 检查进程本身，并让 Readiness 反映依赖可用性。

### 恢复与验证

将 Redis Service selector 恢复为 `app=redis`，确认 EndpointSlice 重新出现 Redis 端点；将 API Liveness Probe 路径恢复为 `/api/healthz` 并等待 Deployment rollout 完成。最终从 `localhost:8080` 请求 `/api/readyz`，获得 HTTP 200，检查结果显示 PostgreSQL 与 Redis 均为 `ok`。

### 面试表达示例

> 我把 Redis Service 的 selector 改成了与 Redis Pod 不匹配的标签，随后检查 EndpointSlice，发现端口和端点都为空，定位到 Service 后端发现链路，而不是直接判断 Redis 进程崩溃。此时记录中的两个 API Pod 仍是 Running 且 Ready，但我没有在故障期间保存业务请求或 API 健康检查结果，所以不会夸大为 API 已经发生业务中断。恢复 `app=redis` 后，EndpointSlice 重新出现 `10.244.0.8:6379`；再恢复 API 探针配置并验证 `/api/readyz` 返回 200，PostgreSQL 和 Redis 检查均通过。

### 常见追问

- **Service 存在为什么仍没有可用后端？** Service 对象存在不代表 selector 一定能匹配 Pod；需检查 selector、Pod labels 和 EndpointSlice。
- **EndpointSlice 的端点为空能证明 Redis Pod 已崩溃吗？** 不能。它说明该 Service 当前没有选中的端点；还要检查 Redis Pod 状态、标签及 selector。
- **为什么实验中 API Pod Ready 不能证明 Redis Service 正常？** Pod 状态与另一个 Service 的端点状态是不同层面的观测；应分别检查 API Pod、Redis Service/EndpointSlice，并在故障时执行实际请求验证。
- **Liveness 与 Readiness 的探测目标应如何区分？** Liveness 关注进程是否应重启；Readiness 关注是否应接收流量。将依赖健康检查用作 Liveness 可能把依赖故障转化为容器重启。

## 实验结论

- 实验已完成。Redis Service 的 selector 被改为不匹配值后，EndpointSlice 未列出端口或端点；恢复 selector 后，端点恢复为 `10.244.0.8:6379`。
- API Liveness Probe 路径先改为 `/api/readyz`，最终恢复为 `/api/healthz`；恢复配置后的 rollout 成功，`/api/readyz` 返回 HTTP 200，PostgreSQL 和 Redis 检查均为 `ok`。
- 现有记录未保存 Redis selector 异常期间的 API 业务影响验证，因此结论限于 Service/EndpointSlice 状态，不推断未观测到的请求失败。
