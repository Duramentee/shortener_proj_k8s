# 实验七：优雅退出与点击数据持久化

## 面试复盘卡

### 一句话结论

将点击写回周期设为 `5m` 后，创建并访问短链，观测到 Redis 中 `clicks:wZ3pDK` 为 `1`、PostgreSQL 中对应记录仍为 `0`。删除一个 API Pod 时，日志记录收到停止信号并完成服务停止；Pod 被替换后，PostgreSQL 中点击数变为 `1`。这组前后数据与停止日志共同支持“Pod 正常优雅退出时，待写回点击数据被持久化”的结论。

### 场景与实验步骤

- **验证对象：** API 后台点击写回与 Pod 终止时的优雅退出流程。
- **配置：** 将 `api-config` 中的 `CLICK_FLUSH_INTERVAL` 设为 `5m`，并滚动重启 API 使环境变量生效。
- **制造待写回数据：** 创建短链 `wZ3pDK` 并访问该短链一次。
- **触发终止：** 检查 Redis/PostgreSQL 计数后，删除一个 API Pod，观察退出日志、替代 Pod 及数据库计数。

### 观测结果与证据

| 阶段 | 实验记录 | 说明 |
|---|---|---|
| 点击前后访问 | 创建短链返回 HTTP 201；访问短链返回 HTTP 302 | 请求成功，产生一次点击 |
| Pod 终止前 | Redis `clicks:wZ3pDK` 为 `1`，PostgreSQL `links.clicks` 为 `0` | 点击计数已进入 Redis，但尚未反映到数据库 |
| 终止日志 | 记录后台写回协程收到停止信号、服务开始优雅退出，随后服务已停止 | 证明进程收到停止流程并完成退出；日志未单独打印写回 SQL |
| Pod 替换后 | PostgreSQL 中 `wZ3pDK` 的 `clicks` 为 `1`；两个 API Pod 均为 `1/1 Running` | 数据库最终计数与 Redis 中待写回值一致，替代 Pod 已就绪 |
| 收尾验证 | 将写回周期设为 `5s` 并滚动重启；`/api/readyz` 返回 HTTP 200 | 实验后应用仍可用，依赖检查通过 |

### 根因与机制

点击计数在该实验观测阶段先存放在 Redis，PostgreSQL 中的计数尚未更新。Pod 通过 Kubernetes 正常终止时，应用收到停止信号；日志显示后台写回协程和服务进入退出流程。Pod 替换后查询数据库，计数从 `0` 变为 `1`，与终止前 Redis 中的计数相符，说明该次正常退出路径完成了数据落库。

该结论仅适用于本次记录到的正常 Pod 删除/优雅退出路径。实验没有测试强制终止（例如超过 grace period 后被 SIGKILL）、节点突然掉电或 Redis 自身数据丢失，因此不能据此保证这些场景下同样不会丢数据。

### 恢复与验证

实验收尾时将 `CLICK_FLUSH_INTERVAL` 设为 `5s` 并滚动重启 API。Deployment rollout 成功，随后 `/api/readyz` 返回 HTTP 200。响应体显示 PostgreSQL、Redis 检查均为 `ok`，可作为实验后的服务健康验证。

### 面试表达示例

> 我先把点击写回周期设为 5 分钟，创建短链并访问一次。删除一个 API Pod 前，Redis 中该短链点击数是 1，而 PostgreSQL 仍是 0，说明存在尚未写回的计数。删除 Pod 后，日志记录写回协程收到停止信号并完成服务退出；新 Pod Ready 后再次查 PostgreSQL，点击数变为 1。这个结果验证了本次正常优雅退出路径能够把待写回计数持久化，但我不会把它外推为强制杀进程或节点故障下也绝不丢数据。

### 常见追问

- **为什么 Redis 是 1 而数据库还是 0？** 实验观测时点击计数已写入 Redis，但数据库尚未到定时写回时点；这正是用来验证退出时写回行为的待持久化状态。
- **Pod 被删除时应用会立刻被杀掉吗？** 正常删除会先进入终止流程并向容器发送停止信号，应用可在宽限期内完成清理；超过宽限期仍未退出才可能被强制终止。
- **这是否证明任意故障下都不会丢点击？** 不能。实验只验证了本次正常优雅退出路径，没有覆盖 SIGKILL、节点故障、Redis 故障或写回失败。
- **如何验证不是只看日志得出结论？** 对同一短链分别查询 Redis 与 PostgreSQL，并在 Pod 终止前后对比持久化计数；同时检查替代 Pod Ready 和业务健康接口。
