# Kubernetes 故障排查思路总结

本文将阶段 6 前四个实验串成一套可复用的排障方法。实验记录保留了具体命令和现场输出；本文侧重回答：出现故障时先看什么、如何逐层缩小范围、如何用证据判断根因，以及怎样证明服务已经恢复。

## 核心原则

> 从用户可见的症状出发，沿请求链路逐层检查；根据证据定位故障阶段，验证根因后再恢复，并通过端到端请求验收。

排障不是看到一个异常状态就立刻修改配置，而是建立一条可以复核的因果链：

```text
用户症状
  -> 入口与访问路径
  -> Service 与就绪端点
  -> Pod / 容器状态
  -> Events 与应用日志
  -> 配置和依赖
  -> 根因验证
  -> 恢复与端到端验收
```

每一步都应回答一个具体问题，并记录“观察到的事实”和“当前假设”。只有证据支持的部分才能作为结论；尚未验证的推断应明确标注。

## 一、先固定故障范围和访问路径

先明确以下信息：

- 哪个用户功能失败：页面加载、API 请求、短链跳转，还是点击统计？
- 具体请求路径、HTTP 状态码、错误响应和发生时间是什么？
- 故障是持续发生还是间歇发生？影响全部请求还是部分副本/功能？
- 请求通过什么入口到达集群：本机端口转发、NodePort、Ingress，还是其他代理？
- `kubectl` 当前连接的是哪个 context 和 namespace？

推荐先检查 context，并从客户端复现一条有代表性的请求：

```bash
kubectl config current-context
curl -i --max-time 5 http://localhost:8080/api/healthz
curl -i --max-time 5 http://localhost:8080/api/readyz
```

如果本机端口转发未运行，`localhost:8080` 连接失败只能说明本机入口没有监听，不能据此判断 Kubernetes 中的 API 已故障。反之，HTTP 502 表示请求到达了一个能返回响应的代理，但不单独说明上游为什么失败。应先区分入口问题和集群内服务问题，再继续向后追踪。

## 二、沿请求路径检查 Service 与后端

当代理可访问但 API 请求失败时，检查 Service 选择条件和 EndpointSlice：

```bash
kubectl get svc api -n shortener -o yaml
kubectl get pods -n shortener -l app=api --show-labels -o wide
kubectl get endpointslice -n shortener \
  -l kubernetes.io/service-name=api -o yaml
```

核对三件事：

1. Service 的 `spec.selector` 是否与目标 Pod 的标签匹配。
2. EndpointSlice 是否包含预期后端地址。
3. 端点的 `conditions.ready` 是否为可接收流量的状态。

Service 对象和 ClusterIP 存在，不代表 Service 一定有可用后端。阶段 6 **实验三**中，API Pod 仍然 Ready，但 Service selector 被改成不匹配的值，EndpointSlice 没有端点，经 Web 访问 API 返回 502。证据把故障定位在 Service 到 Pod 的服务发现链路，而不是 API 进程。详见[实验三：Service Selector 不匹配](/home/drow/k8s_proj/code/shortener/k8s/doc/实验3.md)。

## 三、判断 Pod 是否创建、启动并就绪

```bash
kubectl get deploy,rs,pods -n shortener -o wide
kubectl describe pod <pod-name> -n shortener
kubectl rollout status deploy/api -n shortener --timeout=90s
```

重点区分以下信号：

| 观察到的信号 | 初步含义 | 下一步验证 |
|---|---|---|
| `ErrImagePull` / `ImagePullBackOff` | 节点未能取得声明的镜像；容器通常尚未成功启动 | 镜像完整名称、策略、Events、节点运行时镜像清单 |
| `Running` 且 `0/1 Ready` | 容器正在运行，但未通过就绪条件 | 探针配置、探针 Events、Pod 条件、EndpointSlice |
| `RESTARTS` 增长 | 容器曾退出或被 kubelet 重启 | `Last State`、Liveness Events、当前和 previous 日志 |
| rollout 超时 | Deployment 在时限内未满足期望更新状态；这只是控制器状态，不是根因 | 新旧 ReplicaSet、可用副本、Pod 状态及 Events |

`Running`、`Ready`、`Available` 分别描述不同层次，不能互相替代。Restart 次数是累计值，应比较实验前后的变化，并查看 `Last State`，不能仅凭非零计数判定当前故障。

阶段 6 **实验一**中，新 Pod 进入 `ImagePullBackOff`、重启次数为 0，说明失败发生在镜像准备阶段，并无证据表明 API 进程已启动后崩溃。Events 显示拉取请求因连接本机代理被拒绝；这证明本次拉取未成功，但不能证明远端镜像标签不存在。检查 kind 节点的镜像应使用节点内的 `crictl images`，宿主机 `docker images` 不能代表节点 containerd 的镜像清单。详见[实验一：镜像拉取失败](/home/drow/k8s_proj/code/shortener/k8s/doc/实验1.md)。

阶段 6 **实验二**中，新 Pod 为 `Running`、`0/1 Ready`、重启次数为 0；Readiness Probe 请求错误路径收到 HTTP 404，导致 Pod 未就绪并阻塞 rollout。Readiness 失败影响流量接收与可用副本，不会直接重启容器；Liveness 连续失败达到阈值才会触发重启。详见[实验二：Readiness Probe 配置错误](/home/drow/k8s_proj/code/shortener/k8s/doc/实验2.md)。

## 四、用 Events、日志和配置建立因果关系

```bash
kubectl get events -n shortener --sort-by=.lastTimestamp
kubectl logs <pod-name> -n shortener --all-containers=true
kubectl logs <pod-name> -n shortener --previous
kubectl describe deploy api -n shortener
kubectl get cm api-config -n shortener -o yaml
```

- **Events** 记录 Kubernetes 观察到的调度、镜像拉取、探针失败、容器创建与重启等事件。
- **当前日志** 用于查看正在运行容器的启动和请求情况。
- **`--previous` 日志** 用于查看同一 Pod 中上一个已终止容器实例的输出。
- **配置对象** 用于确认控制器声明了什么；应用启动日志可进一步确认进程实际读取了什么。

阶段 6 **实验四**中，错误服务名产生 `lookup redis-wrong` 超时，是 DNS 解析失败的直接证据。错误端口实验的 Events 则记录健康探针连接 API Pod 的 `:8080` 被拒绝；它不能被转述成“Redis 的 `:6380` 拒绝连接”。应核对错误信息指向的目标、应用日志、已加载配置及 Redis Service/Endpoints，区分观察事实与对上游原因的推断。详见[实验四：Redis 依赖配置故障](/home/drow/k8s_proj/code/shortener/k8s/doc/实验4.md)。

另一个重要边界是配置生效方式：通过环境变量注入的 ConfigMap 值不会自动修改已运行进程的环境。修改后通常需要创建新 Pod，例如执行 Deployment 滚动重启，并确认新 Pod 读取了预期值。

阶段 6 **实验五**中，独立内存压力 Pod 实际以 `OOMKilled`、退出码 137 终止；另一个隔离 CPU burner 在 `100m` limit 下采样为约 `98–101m`，cgroup 记录 763 个调度周期中 746 个发生节流。两个临时 Pod 均在采证后删除，API Deployment 保持 2/2 Ready，健康检查返回 HTTP 200。详见[实验五：资源限制观测——OOMKilled 与 CPU 节流](/home/drow/k8s_proj/code/shortener/k8s/doc/实验5.md)。

## 五、验证假设、恢复服务并完成验收

定位到最可能的根因后，先检查拟执行操作的作用对象和影响范围，再做最小范围的可逆修复。修复后至少完成以下检查：

```bash
kubectl rollout status deploy/api -n shortener --timeout=90s
kubectl get deploy,pods -n shortener -o wide
kubectl get endpointslice -n shortener \
  -l kubernetes.io/service-name=api -o yaml
curl -i --max-time 5 http://localhost:8080/api/healthz
curl -i --max-time 5 http://localhost:8080/api/readyz
```

根据故障类型增加验收项：

- Deployment 的期望副本已更新，所有预期副本均 Ready。
- Service selector 与 Pod 标签一致，EndpointSlice 中存在符合条件的端点。
- API 健康接口返回预期状态；就绪接口中 PostgreSQL、Redis 检查通过。
- 从用户实际使用的入口验证关键业务请求，而不只验证 Pod IP 或单个内部接口。
- 如涉及数据持久化或异步写回，还要单独确认数据结果符合预期。

`kubectl rollout undo` 可以恢复 Deployment 的历史 Pod 模板，但不等同于把所有资源都恢复到仓库文件中的状态。例如，通过 `kubectl patch` 修改过的 Service 或 ConfigMap 不一定随 Deployment 回滚。逐项恢复相应资源，并核对集群配置与声明式清单保持一致。

## 六、面试时的组织方式

建议按以下六点陈述一次故障处理经历：

1. **症状：** 哪个功能失败，用户侧观察到了什么？
2. **影响范围：** 影响哪些请求、副本和依赖？哪些功能仍正常？
3. **证据：** Pod、Service、EndpointSlice、Events 和日志分别显示什么？
4. **根因：** 哪个资源或配置导致故障？哪些是直接证据，哪些仍是推断？
5. **恢复：** 修改或回滚了什么，为什么该操作影响范围可控？
6. **验收与预防：** 用什么端到端检查证明恢复？如何避免同类问题？

可复用的表达模板：

> 用户侧观察到 **[具体症状]**，影响范围是 **[实际影响]**。我先检查 **[入口/Service/Pod]**，发现 **[关键证据]**；再通过 **[Events/日志/配置]** 验证，确认直接原因是 **[根因]**。我通过 **[修复或回滚动作]** 恢复，并以 **[副本、端点、健康接口及业务请求]** 验证服务恢复。当前证据能证明 **[已证实事实]**，但不能据此断言 **[未被证明的结论]**。

## 一页速查

```text
1. 复现症状：请求路径、状态码、时间、影响范围
2. 确认入口：context、namespace、本机端口转发或代理是否工作
3. 检查后端：Service selector -> Pod labels -> EndpointSlice/ready
4. 检查工作负载：Deployment/ReplicaSet -> Pod 状态 -> 重启与探针
5. 查直接证据：Events -> 当前/previous 日志 -> 配置与依赖
6. 验证假设：一次只改一个因素，优先使用可逆操作
7. 恢复验收：副本 Ready、端点正常、健康检查和业务请求成功
8. 复盘表达：症状、范围、证据、根因、恢复、验收
```
