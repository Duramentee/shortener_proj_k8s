# 实验四：依赖配置故障——Redis DNS 名称与端口

## 面试复盘卡

### 一句话结论

通过修改 API 使用的 `REDIS_ADDR`，分别注入 Redis Service 名称错误和端口错误。错误名称的日志直接记录 DNS 查询 `redis-wrong` 超时并导致 API 退出；错误端口时，Pod Events 记录 API 自身健康探针连接被拒绝及容器重启。恢复为 `redis:6379` 后，应用日志确认 Redis 连接成功，Readiness 检查恢复为 HTTP 200。

### 场景与故障注入

- **故障对象：** `api-config` ConfigMap 中的 `REDIS_ADDR`，该值通过环境变量传入 API 容器。
- **实验 A：DNS 名称错误：** 将地址设置为 `redis-wrong:6379`，然后滚动重启 API。
- **实验 B：端口错误：** 将地址设置为 `redis:6380`，再次滚动重启 API。
- **恢复：** 将地址恢复为 `redis:6379` 并重启 API，使新 Pod 使用恢复后的配置。

### 证据与诊断

#### A. DNS 名称错误

1. 配置日志确认 API 实际读取了 `REDIS_ADDR=redis-wrong:6379`。
2. 应用日志记录 `lookup redis-wrong: i/o timeout`，随后记录 Redis 连接失败及服务退出。
3. 这组应用级证据表明，API 未能通过集群 DNS 解析该服务名，并在启动依赖阶段退出。应进一步核实 Service 名称、命名空间、DNS 以及网络策略；在本实验中，错误服务名是故障注入项。

#### B. 端口错误

1. 配置日志确认新 API Pod 读取了 `REDIS_ADDR=redis:6380`。
2. Events 记录 Liveness/Readiness 对 API Pod `:8080` 的 HTTP 探测出现 `connect: connection refused`，随后记录容器因 Liveness 失败而重启以及重启退避。
3. 这里的 `connection refused` 目标是 **API Pod 的 8080 端口**，不是 Redis 的 6380 端口。它直接证明探针执行时 API HTTP 监听端口不可连接；结合错误的 Redis 地址可将故障定位到依赖配置路径，但当前保存的记录未包含一条明确的 Redis `redis:6380` 拒绝连接日志。面试时应区分探针观察到的直接事实与推断的上游原因。

### 依赖配置与探针机制

ConfigMap 作为环境变量注入容器后，已运行进程不会因为 ConfigMap 更新而自动重载该环境变量。滚动重启会创建使用新配置的 Pod，因此实验通过 `kubectl rollout restart deploy/api -n shortener` 使变更生效。

当应用在启动阶段要求 Redis 可用时，错误的 DNS 名称或端口可能使应用启动失败或无法监听 HTTP 端口。此时 Liveness/Readiness 对 API 端口的失败是外部症状；应结合容器日志中的依赖连接错误、实际加载配置、Redis Service/Endpoints 和 Pod Events 建立因果链，不能仅凭探针 `connection refused` 就断言 Redis 端口拒绝连接。

### 恢复与验证

将 ConfigMap 中的 `REDIS_ADDR` 恢复为 `redis:6379` 并滚动重启。恢复后的 API 日志记录配置为 `redis:6379`、Redis 连接成功，且 `/api/readyz` 检查返回 HTTP 200。验收时还应确认所有 API 副本 Ready，并验证对外请求，而不能只以单条容器日志作为完整恢复证明。

### 面试表达示例

> 我在 API 的 ConfigMap 中分别注入了错误的 Redis 服务名和错误端口，并在每次变更后重启 Deployment 让环境变量进入新容器。服务名错误时，应用日志出现 `lookup redis-wrong` 超时并报告 Redis 连接失败；端口错误时，Pod Events 显示 API 的 8080 健康探针连接被拒绝，容器随后重启。我特别区分了探针目标端口与 Redis 目标端口：Events 里的拒绝连接指向 API，而不是直接证明 Redis 端口拒绝。恢复 `redis:6379` 后，日志确认 Redis 连接成功，Readiness 检查返回 200。

### 常见追问

- **更新 ConfigMap 后为什么需要重启？** 通过环境变量消费的 ConfigMap 值在容器创建时进入进程环境，不会自动修改已运行进程的环境变量；应滚动重启或采用明确支持动态重载的配置机制。
- **DNS 错误与端口错误如何区分？** DNS 错误常见证据是 `lookup <name>`、`no such host` 或解析超时；端口/网络层问题需进一步观察解析是否成功以及 TCP 连接错误。检查时可分开验证服务名解析、Service 端口和 Endpoint/Pod 端口。
- **探针连接被拒绝说明什么？** 说明探测目标的 TCP 连接未建立；需确认目标地址和端口。它不自动说明依赖 Redis 端口不可达。
- **为什么不能只通过 `kubectl get pods` 判断？** Pod 的 `Running`、`Ready` 与应用依赖状态是不同层次；结合重启次数、Events、容器日志、ConfigMap 实际值及依赖 Service 状态才能定位根因。
